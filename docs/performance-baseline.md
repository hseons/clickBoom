# ClickBoom 性能测量手册

目标：用可复现的采样建立单屏基线，再决定是否调整全屏复查、输入派发或绘制；1.10 起另有内置的自适应预算，按运行时绘制耗时自动收敛（见文末「1.10 自适应预算与验证」）。采样工具独立运行，不修改 App、设置或输入事件。

下面的基线步骤以 **1.7.0（22）Release** 为起点，做改动前后对照时保持同一套场景和预设即可。已完成的一次 1.9.0 实测（12 场景 ×3，含 1.11.0 对照与热点）见[性能基线结果](performance-baseline-results.md)。

## 环境记录与准备

| 固定项 | 记录模板 |
| --- | --- |
| 系统与设备 | 日期、macOS 版本和 build、机型/芯片、内存、供电和低电量模式 |
| 显示器 | 数量、排列、缩放后的逻辑分辨率、刷新率；注明横屏或竖屏 |
| App | 版本/build、DMG SHA-256、二进制架构、输入监控已授权、目标测试进程 PID（仅本地） |
| 外部应用 | 固定同一空白内容、窗口/系统全屏模式；记录应用和版本，不记录窗口标题 |
| 输入 | 鼠标型号、连接方式、已知回报率（未知则注明）、移动路线和节奏、点击频率、手动或自动 |
| 设置 | 点击特效/粒子数/时长/连点增强、聚光环尺寸、拖尾样式/触发方式/时长、排除列表、免打扰时段（开关与起止时间）及全屏静默状态；仅保存合成测试预设 |
| 干扰项 | 是否锁屏、切空间、打开面板；后台构建、索引、更新检查等发生时废弃该次并重跑 |

1. 使用独立的 macOS 测试登录会话，验证 `dist/ClickBoom-1.7.0.dmg` 的 SHA-256 和包内版本。1.6 和 1.7 共用设置域，不要在日常账户并行运行；仅把包复制到另一目录也不会隔离设置。
2. 打开 1.7，确认输入监控、移动监听、状态和效果符合预期；排除/全屏建议使用不播放媒体的空白测试窗口。关掉设置、诊断与预览面板，保持屏幕亮起；每次测量前稳定到指定前台应用与空间。除了当前场景的必要切换，不改变其余设置。
3. 建议从干净偏好默认值开始：火花、8 粒子、400 ms、关闭随机与连点增强；光带、移动即触发、400 ms。聚光环和拖尾默认关闭；全屏静默默认开启，按场景显式切换。关闭/暂停/排除/全屏场景先开启聚光环和拖尾，验证进入状态时两者都被清理且移动监听已停止；诊断只在采样窗口外打开。

## 采样

在仓库根目录执行：

```sh
mkdir -p build
run=$(mktemp -d "$PWD/build/performance.XXXXXX")
xcrun clang -std=gnu17 -O2 -Wall -Wextra -Wconversion -Werror \
  scripts/performance-sample.c -o "$run/performance-sample"
pgrep -x ClickBoom
```

用 `ps -p <PID> -o comm=` 核对路径，并检查相应包的 `Contents/Info.plist`（`CFBundleShortVersionString = 1.7.0`、`CFBundleVersion = 22`）。若没有唯一、已核验的测试进程，先确保测试会话仅运行指定包。以下示例把 `12345` 替换为核验过的 PID；5 秒用于切回目标应用，不计入预热。每次采样使用唯一文件名：

```sh
pid=12345
sleep 5; "$run/performance-sample" "$pid" > "$run/idle-off-1.csv"
```

每次 **10 秒预热 + 60 秒采样**，全程保持指定状态和负载。每场景至少 3 次；对照组按轮交错（例如 `idle-off`、`idle-on` 各跑一次再进入下一轮）。进程退出、状态不符、现场有干扰或实际采样超出 60–62 秒时，注明原因并重跑。暂停选 15 分钟；各轮从接近相同的剩余时间起测，避免中途到期。

- CPU：区间内用户态及内核态 CPU 时间增量 / 实际经过时间。100% 表示占满一个核。
- 内存：预热结束及之后约每秒取一次物理内存占用（`phys_footprint`），报告**区间采样峰值**（MiB），不是进程生命周期最大值，也可能漏掉采样间的短峰。
- 唤醒：分别记录 `ri_pkg_idle_wkups`、`ri_interrupt_wkups` 的区间增量。两者不相加，也不当作瓦数、整机能耗或 App 定时器触发次数；本工具不测 WindowServer、GPU 或外部应用的开销。
- 函数热点另跑一轮同样的负载，用 Instruments Time Profiler 或 `/usr/bin/sample "$pid" 15 1 -file "$run/hotspot.txt"`。不在 CPU/唤醒采样时同时挂剖析器。记录主线程的热点函数/路径，区分休眠栈与有效工作；通用符号或权限不足导致无法定位时如实标记。需要帧耗时分布时另做明确标注的开发测量，不用 CPU 百分比代替帧耗时。

## 单屏矩阵

未特别注明时，使用相同的非排除窗口、不开全屏静默；移动在空白内容区域按固定路径（例如左右约 400 pt、每秒一个来回），手动点击可用独立节拍器提示约 3 次/秒。不要用系统按钮或真实工作文档做输入靶点。

| ID | 场景和操作 | 重点检查 |
| --- | --- | --- |
| `disabled` | 总开关关闭；聚光环/拖尾已配置；鼠标静止 | 无活动特效，移动监听与全屏复查停止 |
| `paused` | 总开关开，定时暂停；其余同 `disabled` | 区分暂停状态自己的低频计时与全屏复查 |
| `excluded` | 总开关开，前台应用已排除；其余同 `disabled` | 状态提示排除，清理后无拖尾/粒子 |
| `idle-off` | 总开关开，鼠标静止，聚光环和拖尾关闭，全屏静默关 | 无特效下的进程基线 |
| `idle-on` | 只把 `idle-off` 的全屏静默打开，仍在普通窗口 | 与 `idle-off` 对照，量化 0.5 秒复查路径 |
| `quiet-still` | 免打扰时段设为当前时间前后各 1 小时，聚光环与拖尾开启，鼠标静止 | 检查时段内是否停掉全屏复查与移动监听；与 `idle-on` 对照量化边界计时器的待机开销 |
| `fullscreen` | 全屏静默、聚光环、拖尾均已开启；在非排除应用的系统全屏空间静止 | 确认静默和清理；静止指针退出全屏时另行观察恢复，不混入样本 |
| `spotlight-still` | 只开聚光环，鼠标静止 | 检查静止聚光环是否有持续负载 |
| `spotlight-move` | 同上，持续移动，无点击 | 移动监听、指针跟随与主线程派发 |
| `trail-move` | 只开 400 ms 光带，持续移动，无点击 | 轨迹常规采样与绘制 |
| `trail-max` | 将 `trail-move` 的拖尾设置为界面上限 2000 ms | 长轨迹下采样与绘制；换样式须另做对照 |
| `click-trail` | 同 `trail-max`，持续移动叠加左键点击 | 轨迹与粒子同时存在时的负载；是否接近上限以实测为准 |

前三项也打开全屏静默的设置，验证相应运行状态确实优先于全屏复查；诊断没有复查计时器字段，因此停止判断来自代码条件和热点对照，不以总唤醒数归零为验收标准。多屏/竖屏可用后，分开记录显示器拓扑；复用相同场景和预设，另验跨屏坐标、残留拖尾以及插拔后的恢复，不并入单屏组。

## 1.10 自适应预算与验证

1.9 之前的效果上限是固定的 600 粒子、180 轨迹点和约 60 Hz 派发。固定优化（全屏复查、输入派发、绘制热点）目前都没有可复现的热点证据，因此 1.10 改为按测量结果自动收敛：先测每帧绘制耗时，再决定保留多少元素。

### 档位

| 档位 | 粒子上限 | 轨迹点上限 | 覆盖层帧率 | 降级阈值（p90） | 作为目标档的恢复阈值（p90） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 完整画质 `full` | 600 | 180 | 60 fps | 10.3 ms | 5.5 ms |
| 平衡 `balanced` | 360 | 120 | 60 fps | 10.3 ms | 5.5 ms |
| 节能 `economy` | 220 | 80 | 45 fps | 13.8 ms | — |

阈值按 `帧间隔 × 0.62`（降级）和 `帧间隔 × 0.33`（恢复）计算，留出合成、WindowServer 和系统调度的余量。降级与恢复阈值之间的空档是回差，防止在临界负载上反复切换。

### 判定规则

- 覆盖层每帧记录一次 Canvas 绘制耗时，攒满 60 帧（60 fps 下约 1 秒）后每 8 帧计算一次 p90。用分位数而不是平均值：偶发长帧不会放大成持续压力，10% 以上的帧持续超预算才降级。
- 超出当前档位的降级阈值时降一档，两次变化至少间隔 1.5 秒，一个窗口只降一档。
- 低于目标档的恢复阈值并连续保持 3 秒才升一档；目标档是当前档的上一级，所以从节能恢复要经过平衡档。
- 升级后 6 秒内又降级视为升级失败，暂停自动升级 18 秒。
- 粒子和轨迹全部清空（特效结束、暂停、排除、全屏静默）时回到完整画质并清空窗口，下次动画重新测量；诊断里的「上次采样」保留最近一次结果。
- 只测 Canvas 绘制耗时的 p90，不含合成、GPU 和 WindowServer，不能当作屏幕帧率或能耗读数。

### 固定档位做 A/B

自动档位会跟着负载变化，直接对比两次采样会把档位差异混进结果。需要固定档位时用环境变量 `CLICKBOOM_EFFECT_TIER`，此时只统计不决策：

```sh
launchctl setenv CLICKBOOM_EFFECT_TIER economy   # full / balanced / economy，也接受 off、minimal、0-2
open -a /Applications/ClickBoom.app
# 采样结束后清除，避免影响日常使用
launchctl unsetenv CLICKBOOM_EFFECT_TIER
```

从终端直接跑开发版时也可以 `CLICKBOOM_EFFECT_TIER=balanced .build/debug/ClickBoom`。诊断面板的「性能档位」会标注「（已固定）」。

### 验证矩阵

沿用上面的单屏场景，重点三类，每类至少 3 次、10 秒预热 + 60 秒采样：

| 场景 | 自动档位关注点 | 固定档位对照 |
| --- | --- | --- |
| `idle-on`、`spotlight-still` | 无动画时不应降级，诊断显示「暂无活动帧」 | `full` 与 `economy` 的静止开销应一致 |
| `trail-max`、`click-trail` | 是否降档、降到哪一档、p90 是否随之下降 | `full` vs `economy` 给出手动上下界 |
| `spotlight-move`、连续点击 | 升降档是否抖动（短时间反复变化） | `balanced` 用于确认中间档收益 |

每次采样同时记录：诊断面板的「性能档位」「帧绘制耗时」「预算上限」、同一场景的 CPU %、采样峰值 MiB 和唤醒次数。自动档位的收益体现在同一负载下 CPU 或 p90 低于固定 `full`，且默认场景不降档。

### 验收

- 默认场景（火花 8 粒子、400 ms、光带 400 ms、单屏）全程保持完整画质，p90 低于 10.3 ms。
- 压力场景档位下降后，CPU 或 p90 的改善高于同场景波动范围；没有稳定差异时按「无收益」记录，不继续加码。
- 特效结束、暂停、排除和全屏静默进入后档位回到完整画质，粒子与轨迹归零，诊断不再显示活动帧。
- 升降档不导致可见的样式变化：颜色、笔触、按钮映射和拖尾形状只受数量上限影响。
